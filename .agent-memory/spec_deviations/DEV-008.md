# DEV-008: btRaycastVehicle has no removeWheel; detach reindexes only the ECS side

**Date:** 2026-08-08
**Category:** spec_deviations
**Related Docs:** docs/05_vehicle_part_system.md#D05-S5.5, docs/06_physics_simulation.md#D06-S5.5
**Status:** superseded (by DEV-015)

## Summary
D05-S5.5 step 2 calls `vehicleController.removeWheel(index)` when a wheel part detaches. gdx-bullet 1.14.2's `btRaycastVehicle` exposes `addWheel` and no removal of any kind, so `PartDetachment` performs the wheel-index re-densification D05-R24 requires on the ECS side and leaves the native controller untouched.

## Details

**Deviates from:** `docs/05_vehicle_part_system.md#D05-S5.5` step 2 — `vehicleController.removeWheel(index)` followed by `reindexRemainingWheels(vehicle)`.

The full wheel surface of `com.badlogic.gdx.physics.bullet.dynamics.btRaycastVehicle` in 1.14.2 is:

```
btWheelInfo addWheel(Vector3, Vector3, Vector3, float, float, btVehicleTuning, boolean)
int         getNumWheels()
btWheelInfo getWheelInfo(int) / getWheelInfoConst(int)
void        setWheelInfo(SWIGTYPE_p_btAlignedObjectArrayT_btWheelInfo_t)
Matrix4     getWheelTransformWS(int)
void        updateWheelTransform(int, boolean)
```

There is no `removeWheel`. Bullet's C++ `btRaycastVehicle` has none either — its `m_wheelInfo` array is append-only in the public API. `setWheelInfo` takes an opaque SWIG pointer to a `btAlignedObjectArray<btWheelInfo>` that gdx-bullet gives no way to construct, so it is not a route either.

What is implemented today (`PartDetachment.removeWheel`):

- the wheel is removed from `VehicleChassisComponent.wheelEntities` and the tail is shifted down, keeping the array dense;
- `wheelCount` is decremented;
- every surviving `WheelControllerComponent.wheelIndex` is rewritten to its new position.

That is the whole of (D05-R24)'s requirement *except* the native array, which stays as it was.

**Consequence while this stands:** nothing yet creates a `btRaycastVehicle` — `VehicleControlSystem` (slot 7) is unwritten and `VehicleChassisComponent.vehicleController` is always null — so the gap has no observable effect. It becomes real the moment that system exists: a detached wheel would keep ray-casting and applying suspension force at its old position.

**Intended remedy:** the only route Bullet leaves is to rebuild the controller — dispose the `btRaycastVehicle`, construct a new one, and re-add the surviving wheels from their (already correct) `WheelControllerComponent` state. That belongs to `VehicleControlSystem`, the class that builds the controller and owns its tuning, not to a structural operation in the `vehicle` package. The ECS bookkeeping done here is exactly what that rebuild needs to read.

## Rationale / Context
A session implementing `VehicleControlSystem` will read D05-S5.5, look for `removeWheel`, not find it, and either lose an afternoon on the SWIG array type or assume detachment is broken. It also has to know that the ECS indices are already correct, so the rebuild is a re-add and not a re-derivation.

## Impact
`game-core` `vehicle` (`PartDetachment`), and the future `VehicleControlSystem` (slot 7). Affects D05-S5.5 step 2 and (D05-R24).

**Blueprint Disposition: DOC_SHOULD_CHANGE.** D05-S5.5 step 2 names an API that does not exist in the pinned library (D02-R1 fixes gdx-bullet 1.14.2). The step should say that removing a wheel rebuilds the controller from the remaining `WheelControllerComponent` state, and (D05-R24) should keep the index re-densification requirement unchanged. Amendment deferred to the session that implements `VehicleControlSystem` and can write the rebuild the amended text describes.
