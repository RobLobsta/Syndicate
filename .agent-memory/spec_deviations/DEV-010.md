# DEV-010: the asset loader does not read collision meshes; they arrive through a seam

**Date:** 2026-08-09
**Category:** spec_deviations
**Related Docs:** docs/08_asset_pipeline.md#D08-S5.3, docs/02_technical_architecture.md#D02-S4.5, docs/03_runtime_modes.md#D03-S5.5

**Status:** resolved

## Summary
D08-S5.3's `AssetRegistry.load` calls `GltfLoader.loadNode` to get a part's collision geometry out
of `mesh.glb`. `game-core` has no glTF reader and cannot have gdx-gltf's, so `AssetLoader` takes the
mesh from a `CollisionMeshSource` supplied by its caller and reports A503 when that returns nothing.

## Details

**Resolved 2026-08-09 by `GltfReader` and `GltfCollisionMeshSource` (DEC-035).**

**Deviates from:** `docs/08_asset_pipeline.md#D08-S5.3` step 2 — `collisionMesh = GltfLoader
.loadNode(p.path + "/mesh.glb", node = def.assets.collisionSource.node)` and the shard-mesh loop
below it. That step is where D08-R12's choice of glTF as the runtime mesh format meets D02-R9's
headless-safety check, and the two cannot both hold inside `game-core`.

The importer D08-R12 names is gdx-gltf, and gdx-gltf builds libGDX `Mesh` objects — GPU buffers that
require a GL context. G17 requires every gameplay system to run headless and D02-S4.5 puts gdx-gltf
outside `game-core`'s dependency set entirely. This is the same wall DEC-008 hit in
`test-environment`, which answered it by writing a ~200-line `GlbReader` of its own; DEC-013 then
removed gdx-gltf from that module's dependencies for the same reason.

`game-core` could have the same reader, and should. What it must not have is a partial one written
in passing: the reader decides what a part's collision hull is, and every mass, inertia and contact
in the game follows from it.

So the loader reads everything that is text — `materials.json`, `part.json`, `assembly.json`,
including the `assets.collisionSource` reference itself — and asks for the geometry:

```java
MeshData meshFor(AssetId partTypeId, String collisionSourceRef, Path partDirectory);
```

Today's only implementations are in tests.

Two further parts of D08-S5.3 are out of scope with it and not otherwise recorded: shard hulls are
not pre-built at load (`FractureSystem` builds them on demand from the manifest, which is where the
shard meshes already come from), and `asset-index.json` is not read — the loader walks the directory
tree instead, because the index is produced by `asset-pipeline`, which is unimplemented.

## Rationale / Context
Without this, the next session sees a loader that reads a part's mass and hit points off disk but
takes its mesh from a lambda, and reads it as an unfinished thought rather than a bounded one. It
also records why the obvious shortcut — adding gdx-gltf to `game-core` — is not available, which is
a mistake that would pass code review and break the dedicated server.

## Impact
`game-core` `asset` (`AssetLoader`). Blocks loading real content end to end, and therefore blocks
`asset-pipeline` producing an index the game consumes. Affects D08-S5.3 and D08-S4.5 (D08-R12).
Related to DEC-008 and DEC-013.

**Blueprint Disposition: IMPL_SHOULD_CHANGE.** D08-S5.3 is right about where collision geometry comes
from; `game-core` is missing the headless reader that gets it there, which is a gap in the
implementation rather than in the specification. The `CollisionMeshSource` seam is the shape of that
fix, not a replacement for it: it takes the part directory and the raw `collisionSource` string
(`mesh.glb#node=<name>`), which is everything D08-S5.3 passes to `loadNode`.
