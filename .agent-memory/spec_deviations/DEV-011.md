# DEV-011: the dedicated server runs its own loop; no libGDX Application is created

**Date:** 2026-08-09
**Category:** spec_deviations
**Related Docs:** docs/03_runtime_modes.md#D03-S5.1, docs/03_runtime_modes.md#D03-S5.4, docs/02_technical_architecture.md#D02-S4.5

**Status:** active

## Summary
D03-S5.1 step 4 wraps the headless server in a `HeadlessApplication`. `ServerMain` sets
`Gdx.files = new HeadlessFiles()` and runs `HeadlessLoop` on the main thread instead.

## Details
**Deviates from:** `docs/03_runtime_modes.md#D03-S5.1` step 4, and the loop ownership D03-R12 assumes —
`app = new HeadlessApplication(listener, headlessConfig(config.tickRateHz))` and the
`SyndicateApplicationListener` whose `create()` ends by starting the loop.

D03-S5.1 gives the Application two jobs: "provides files and the app lifecycle with no GL context".

The **files** half is real and is kept — `Gdx.files` is assigned a `HeadlessFiles`, which needs no
Application, has no GL context, and leaves G17 exactly as intact as the full backend would. Nothing
in the current stack reads it (`AssetLoader` uses `java.nio`), but a null `Gdx.files` is a trap for
whatever does first.

The **lifecycle** half is the conflict. `HeadlessApplication` runs its own loop, calling the
listener's `render()` at its configured rate; D03-S5.4 (D03-R12) specifies a different loop, with a nanosecond
tick target, a coarse-sleep-then-spin wait and an overload resync at 30 ticks behind. Two loops in
one process each think they own the tick rate: either `HeadlessLoop.start()` blocks the backend's
thread for the life of the server, or the backend drives ticks and D03-S5.4's pacing rules are
inert. Running D03-S5.4's loop on the main thread is the only arrangement in which that section is
implemented rather than described.

The rendering client is unaffected: it will need a real `Lwjgl3Application` for its window, and
D03-S5.3's `ClientLoop` is written as a `render(frameDeltaSeconds)` callback, which is exactly what
a backend provides.

## Rationale / Context
A session that adds a subsystem expecting `Gdx.app` — an `AssetManager`, a libGDX
`Preferences` store, anything scheduling with `Gdx.app.postRunnable` — will find it null and read
that as an oversight rather than a decision. It should instead know that the Application was left
out on purpose, that `Gdx.files` is provided directly, and that reintroducing the backend means
deciding which loop owns the tick.

## Impact
`game-server-headless` (`ServerMain`, `ServerRuntime`). Affects D03-S5.1 step 4 and D03-S5.5.

**Blueprint Disposition: DOC_SHOULD_CHANGE.** D03-S5.1's step 4 is written for both executables at
once and the headless branch does not survive contact with D03-S5.4, which the same document
specifies in more detail. The amendment is to say that a headless process installs `HeadlessFiles`
and runs `HeadlessLoop` directly, and that the Application shell is the rendering client's.
