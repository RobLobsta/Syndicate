# DEV-015: a detached wheel's native slot is disarmed, and indices never renumber

**Date:** 2026-08-10
**Category:** spec_deviations
**Related Docs:** docs/05_vehicle_part_system.md#D05-S5.5, docs/06_physics_simulation.md#D06-S5.5

**Status:** resolved

## Summary
**Resolved 2026-08-17.** D05-R24, D05-S5.5 and AC-D05-12 now say the slot is retired in place and indices are stable.

Supersedes DEV-008. `btRaycastVehicle` still has no `removeWheel`, so a detached wheel keeps its slot
in the native controller. That slot's stiffness, damping, maximum force, friction, engine force,
brake and steering are set to zero, and the surviving wheels **keep** their indices rather than being
re-densified as (D05-R24) requires.

## Details

**Deviates from:** `docs/05_vehicle_part_system.md#D05-S5.5` step 2 —
`vehicleController.removeWheel(index)` and `reindexRemainingWheels(vehicle)`.

**Why re-densifying is worse than not.** DEV-008 implemented the ECS half of D05-R24 on the reasoning
that a later controller rebuild would want it. It does not: `WheelControllerComponent.wheelIndex` is
an index into the native array, and that array does not densify. Renumbering the survivors therefore
pointed each of them at a neighbour's suspension — wheel 2 steering wheel 1's corner — which is the
exact silent failure D05-R24 exists to prevent, introduced by the code meant to satisfy it. It was
unobservable while `vehicleController` was always null and became real the tick `VehicleControlSystem`
was written.

**What replaces it.** `wheelEntities[0..wheelCount)` stays dense and `wheelIndex` stays fixed. Every
loop over wheels already iterates the first and addresses Bullet through the second, so a dense ECS
list over a sparse native array is the shape they were written for.

**Why not rebuild the controller.** DEV-008 named that as the remedy. It means disposing a
`btRaycastVehicle` that is an action registered in the dynamics world, building another, and re-adding
the survivors mid-tick — native churn on the structural path, for a vehicle that loses at most three
wheels in its life. Zeroing nine floats on a `btWheelInfo` achieves the same physics.

**What it still costs.** The vacated slot's ray is still cast every step: one ray per lost wheel per
tick, producing no force. `WheelDetachTest` asserts the force is zero and that a car that has lost a
wheel drives on with exactly three wheels in contact.

## Rationale / Context
D05-R24's requirement is a consequence of an assumption — that removal densifies the array — which
Bullet does not honour. Recorded so the next reading of D05-R24 does not "fix" the indices back.
Candidate blueprint amendment: D05-S5.5 step 2 should say the controller's wheel slot is retired in
place, not removed.

## Impact
`game-core` `vehicle` (`PartDetachment.removeWheel`), and every reader of
`VehicleChassisComponent.wheelEntities` / `WheelControllerComponent.wheelIndex` — slots 7, 15 and 21.

**Blueprint Disposition: DOC_SHOULD_CHANGE.** D05-R24 requires an operation the physics library does
not provide, and its re-densification clause is only correct if the native array densifies too. The
amendment is to say the controller's wheel slot is retired in place and indices are stable for the
life of a vehicle.
