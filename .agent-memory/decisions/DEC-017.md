# DEC-017: wreckVehicle does not fracture the chassis; slot 13 does, one slot earlier

**Date:** 2026-08-08
**Category:** decisions
**Related Docs:** docs/07_damage_destruction_model.md#D07-S5.7, docs/04_entity_component_model.md#D04-S4.4, docs/05_vehicle_part_system.md#D05-S5.5

**Status:** active

## Summary
D07-S5.7's `wreckVehicle` calls `fracturePart` on the chassis, which D04-R13 prohibits as a
system-to-system call. `FractureSystem` (13) instead fractures a destroyed chassis part like any
other — without detaching it, because the chassis cannot be detached (D05-R26) — and `DetachSystem`
(14) treats a chassis part that is *gone or destroyed* as the wreck trigger, one slot later in the
same tick.

## Details
Two blueprint lines meet badly:

- D07-S5.7: `if vehicle.chassisPart.hasFractureData: fracturePart(world, vehicle.chassisPart, tick)`,
  inside `wreckVehicle`, which is `DetachSystem`'s function.
- D07-S5.6: `fracturePart` is `FractureSystem`'s, in slot 13.

Implementing that literally means slot 14 calling slot 13, which D04-R13 forbids for the reason the
schedule exists: causality is the schedule, not a call graph. The alternative — extracting the
shard-spawning into a shared operation the way DEC-016 extracted `detachPart` — was rejected because
it buys nothing here. The schedule already runs 13 before 14 in the same tick, so a destroyed chassis
part reaches `FractureSystem` first, from exactly the same manifest, and produces exactly the shards
`wreckVehicle` would have asked for. What changes is only which system's stack frame they are spawned
on.

Three things this fixes or fixes-by-construction:

1. **`FractureSystem` skips the detach for a chassis part.** It previously called
   `PartDetachment.detach` for every fracturing part, and `detach` throws for the chassis (D05-R26).
   A destroyed fracturable chassis would therefore have thrown mid-tick. It now fractures the part
   and leaves the vehicle's structure alone; the vehicle comes apart one slot later.
2. **`DetachSystem`'s T4 condition reads liveness as well as state.** A fractured chassis part has
   been destroyed by the time slot 14 looks, so its `DamageState` is unreadable. `isChassisDead`
   returns true for a chassis part that is not alive *or* is `DESTROYED`/`DETACHED`, which puts the
   fracturing chassis and the plain one on one path.
3. **The wreck stays one-way without a new field.** D07-S5.7 guards on `vehicle.isWrecked`, which is
   not in the D04-S4.3.2 component catalogue. `wreckVehicle` destroys the vehicle entity, and a
   destroyed entity is immediately not alive and immediately out of every family (D04-S5.5), so
   `world.isAlive(vehicleEntity)` is the guard. Nothing to remember, nothing to replicate, nothing to
   restore on a rollback.

## Rationale / Context
A session implementing the wreck path reads D07-S5.7 top to bottom and writes the `fracturePart` call
it names. That produces either a `game-core` cycle or a second shard-spawning implementation, and the
second one will disagree with the first about scatter, stream order, or mass — a determinism bug that
only shows as a client and server disagreeing about an explosion. Recording the resolution here also
records *why* `FractureSystem` has a chassis special case that reads like an omission.

## Impact
`game-core` `system` (`FractureSystem`, `DetachSystem`). Affects D07-S5.7 `wreckVehicle` and
D07-S5.6. Does not change what the player sees or what is replicated: the same
`PartFracturedEvent` is emitted from the same manifest on the same tick.
