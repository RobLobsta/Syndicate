# DEC-035: the glTF reader lives in game-core and composes node transforms

**Date:** 2026-08-09
**Category:** decisions
**Related Docs:** docs/08_asset_pipeline.md#D08-S4.5, docs/02_technical_architecture.md#D02-S4.5, docs/14_test_environment.md#D14-S5.13

**Status:** active

## Summary
`GltfReader` is a `game-core` class in `dev.syndicate.core.asset`, it composes every node's transform
down from the scene root and applies it to the geometry it returns, and `test-environment`'s
`GlbReader` becomes a thin adapter over it rather than a second parser.

## Details

**Where it lives.** Three placements were possible and only one holds every constraint:

| Option | Verdict | Reasoning |
|---|---|---|
| **`game-core`, own reader** | **CHOSEN** | The dedicated server, the harness and the client all need the same parse, and `game-core` is the only module all three share. DEV-010's disposition already said the gap was here. |
| gdx-gltf in `game-core` | Rejected | Builds libGDX `Mesh` objects — GPU buffers needing a GL context. D02-S4.5 puts gdx-gltf outside `game-core` entirely and G17 forbids it in the module the server shares. This is DEC-008's wall, one module over. |
| Keep two readers | Rejected | The harness already depends on `game-core`, so the duplication bought nothing, and the copy that existed had two defects the shared one does not (below). |

**Why transforms are composed and baked.** The harness's original reader read `POSITION` straight out
of the accessor and ignored the node hierarchy. That was harmless only because every fixture the
Blender tool writes has an identity node transform. Real art does not:

- the Maserati MC20 export carries its Z-up-to-Y-up conversion **and** a 0.9625 uniform scale on its
  root node;
- the Mustang GTD export carries a 0.01 centimetre-to-metre scale on an `FBX` node whose mesh data
  was already in metres, so the car reads as 4.9 cm long.

A reader that skips the hierarchy returns geometry that parses, renders and measures — and is on its
side at a hundredth of its size, with every derived quantity self-consistently wrong. Positions and
normals therefore come back in scene space, with the normal matrix applied and the winding flipped
when a transform has negative determinant.

**What the harness keeps.** `MeshData`'s volume and centroid maths stay independent of the Blender
tool's, because D09-S6.2 makes agreement between two implementations the evidence that both are
right. Sharing a *parser* costs nothing there; sharing the *measurement* would delete the check.

**What the reader does not read**, deliberately: skinning (joint weights are ignored and the node's
own transform used — `GltfReader.skinnedNodeCount` reports the count so a caller can check rather
than assume), morph targets, animations, cameras and lights. A `extensionsRequired` entry is an
error rather than a silent empty mesh, which is what D08-R14 turns Draco off to prevent.

## Rationale / Context
The obvious next move for a session that needs to read a mesh is to reach for gdx-gltf, because
D08-R12 names it and it is already on `game-client`'s classpath. That change compiles, passes review,
and breaks the dedicated server at deploy time. The second-obvious move is to extend the harness's
reader in place, which leaves the game with no reader at all.

The transform half matters more than it sounds: a reader that ignores node transforms fails *silently
and consistently*, so nothing downstream disagrees with anything else. It was found by rendering a
car, not by a test.

## Impact
`game-core` `asset` (`GltfReader`, `GltfModel`, `GltfMeshNode`, `GltfPrimitive`, `GltfMaterial`,
`GltfImage`, `GltfOptions`, `GltfException`, `GltfCollisionMeshSource`), `test-environment`
(`GlbReader` becomes an adapter), `game-server-headless` (`ServerRuntime` uses the real source).
Resolves DEV-010. Extends DEC-008 rather than superseding it: that entry's reasoning about gdx-gltf
and GL contexts is unchanged, and is why this reader exists at all.
