# DEC-036: a model's unit and axis correction lives in import.json, verified

**Date:** 2026-08-09
**Category:** decisions
**Related Docs:** docs/08_asset_pipeline.md#D08-S4.1, docs/00_master_index.md#D00-S5.2, docs/14_test_environment.md#D14-S5.3

**Status:** active

## Summary
The correction that takes a piece of downloaded art into the game's units and axes is recorded once,
in an `import.json` beside the model — scale, then yaw about Y, then translation — and the harness's
`--model` mode applies it *before* it measures, so the numbers in that file are confirmed by the
checks rather than asserted by a comment.

## Details

**The file.**

```json
{ "scaleToMetres": 1.0389227840196078,
  "yawDeg": 180.0,
  "translationM": { "x": 0.0, "y": 0.6669, "z": 0.0 } }
```

Three fields, applied in that order so each can be read independently: the scale is a unit
conversion, the yaw is which way the car faces, the translation drops the origin onto the ground
plane. `dev.syndicate.verify.model.ModelImport` is the implementation; an absent file is the
identity, and a present but unreadable one throws rather than silently becoming no correction.

**Why beside the model rather than in a tool, a constant or the part JSON.** Every tool that touches
the file needs the same three numbers: the checks, the renderer, and eventually the Blender split.
Anywhere else and each re-derives them, and one of them gets it wrong — which is exactly the class of
bug that is invisible, because a wrongly-scaled car is still a perfectly self-consistent car.

**Why the harness applies it before measuring.** This is the part that makes the file trustworthy.
`MODEL-004` (is it in metres), `MODEL-005` (is Y up), `MODEL-006` (is the long axis Z) and
`MODEL-007` (does the origin sit on the ground) all run on corrected geometry, so a wrong
`scaleToMetres` fails the run and the failure message names the factor that would fix it. The
Eclipse's 4.6682 m and the Stampede's 4.9196 m are outputs of that pipeline, not inputs to it.

**What it cannot verify.** Which end of the car is the front. `MODEL-006` can tell that the long axis
is Z and not which way along it the nose points, so `--model` captures a front and a rear
three-quarter view and the yaw is settled by looking at them. That is how the Eclipse's 180° was
found: the dashboard geometry sits at negative Z, the narrow tyres are on the −Z axle, and the render
showed an engine cover where the bonnet should be.

## Rationale / Context
Without this, the next model to arrive gets its scale worked out in a scratch script, used once, and
lost — and the session after that finds a car that is 4% too small and has no way to tell whether
that is the art, the reader or the physics. Recording the numbers is half of it; having the checks
re-derive them on every run is the half that keeps them true.

## Impact
`art-source/vehicles/*/import.json`, `test-environment` (`ModelImport`, `ModelInspector`,
`ModelScene`), `art-source/README.md`. Applies to every piece of source art added afterwards.
