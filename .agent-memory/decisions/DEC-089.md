# DEC-089: every manifest names its transform and its class, and the gate pairs them

**Date:** 2026-08-17
**Category:** decisions
**Related Docs:** docs/09_blender_destruction_tool.md#D09-S4.4, docs/08_asset_pipeline.md#D08-S5.4, docs/15_vehicle_preparation_pipeline.md#D15-S5.7

**Status:** active

## Summary
`fracture_manifest.json` and `deform_manifest.json` both carry `transform` and `destructionClass` as
required fields, and a new asset-gate rule **A510** rejects a manifest that declares neither, that
declares a transform its part's class does not receive, or that sits beside a part also declaring
damage morphs. The tools' refusal (DEC-088) and this gate are independent implementations of one
rule, in the spirit of DEC-041.

## Details
A manifest previously recorded the tool version, the seed, the source hash, the topology hash, the
material and 24 shards — and never said that it was a *fracture* manifest for a *glass* part. So a
consumer could not tell a manifest that should exist from one that should not, and nothing could
catch the tool authoring shards for a steel door (DISC-068).

Two fields, and the second is the one that does the work. `transform` alone would let a `FRACTURE`
manifest sit on a panel; the class is what pairs it against `part.json`. A510 therefore checks four
things, and each has its own message because each sends the reader somewhere different:

1. no `transform` at all — the manifest predates the split and must be regenerated;
2. a transform this file cannot be (`assets.fractureManifest` naming a `DEFORM` manifest);
3. the manifest's class disagreeing with `part.json`'s;
4. the class being one D15-S5.7 gives no shards to — wrong *even when the two files agree*, which is
   why it is a separate branch rather than folded into 3.

**Why a gate as well as the tools.** Everything the tools refuse, they refuse at authoring time. A
manifest that arrived by hand, in a copied directory, or from a tool version predating the split has
never passed a tool's check, and the runtime will not look: nothing in `game-core` consults
`DestructionClass` before fracturing (DISC-068). The gate is the only thing standing between such a
file and a shipped build.

**Why not also refuse at load.** `AssetLoader` deliberately does not, yet: content is decided at the
gate, a strict start already refuses on any A5xx error (D03-S4.4), and a second refusal would be a
second place to change when D15-S5.7 next moves.

## Rationale / Context
The concrete future failure this stops: somebody regenerates one part's shards by hand, pastes the
directory beside another part, and ships a windscreen's shard set under a door's name. Before A510
the only symptom was a door coming apart into curved glass fragments, three sessions later, with
nothing in any log.

The eight shipped glass manifests were regenerated to declare the new fields; that run also moved
their `topologyHash`, which is DISC-069 and not this change.

## Impact
`asset-pipeline` (`AssetIndexBuilder.checkTransformMatchesClass`, three new tests);
`blender-tool` (both manifest builders); `assets/` (eight regenerated manifests).
D08-S5.4 gains the A510 row and two test cases; D09-S4.4's schema gains both fields.
