# DEC-062: a client sends its input from slot 19, because slot 18 is authority-only

**Date:** 2026-08-13
**Category:** decisions
**Related Docs:** docs/04_entity_component_model.md#D04-S4.4, docs/10_networking_multiplayer.md#D10-S5.5

**Status:** active

## Summary
`NetworkReceiveSystem` (19) records the tick's prediction, sends the `InputCommand` packet, and then
applies whatever arrived. D04-S4.4's row for slot 19 was amended in the same commit to say so.

## Details
D04-S4.4 gives slot 18 (`NetworkSendSystem`) the mode filter `authority`, so a pure client has no
send slot at all — and D10-S5.5's `clientTick` plainly sends an input packet every tick. Rather than
widen slot 18's availability, which would put an authority's snapshot builder in a client's
schedule, the client's whole network turn lives in the one slot its mode does schedule.

The internal order matters and is not arbitrary. Prediction is recorded first, because physics ran
at slot 10 and this tick's predicted transform exists only now; the input goes out second; the
snapshot is applied last, so slot 20 finds both halves of the comparison in place.

## Rationale / Context
The alternative reading — that slot 18 is "the send slot" for both roles — makes the mode filter in
D04-S4.4 wrong rather than the code, and a client that ran a snapshot builder would be one refactor
away from a client that authors authoritative state (G15).

## Impact
- `NetworkReceiveSystem.update` does three things in a fixed order.
- D04-S4.4 row 19 now reads "sends this tick's `InputCommand`; applies snapshot, triggers
  reconciliation".
