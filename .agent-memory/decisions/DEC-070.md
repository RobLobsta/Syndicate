# DEC-070: per-surface grip is applied at the wheel, not through Bullet's material callback

**Date:** 2026-08-14
**Category:** decisions
**Related Docs:** docs/16_procedural_arena_generation.md#D16-S4.4, docs/16_procedural_arena_generation.md#D16-S5.10, docs/06_physics_simulation.md#D06-S5.5

**Status:** active

## Summary
The surface under a wheel changes that wheel's `frictionSlip` and rolling resistance inside the
shared vehicle control operation (DEC-061), looked up from the terrain's surface grid at the
suspension ray's contact point. It does **not** go through the terrain body's Bullet friction, and it
does not go through `CF_CUSTOM_MATERIAL_CALLBACK`.

## Details
Both rejected mechanisms are the ones a search for "per-triangle terrain materials in Bullet" returns,
and both are wrong here for the same reason: a ray-cast vehicle's tyres never produce a Bullet contact
point.

- **The static body's `friction`.** `btRaycastVehicle::updateFriction` computes tyre forces from
  `WheelInfo.m_frictionSlip` and the suspension load. The ground body's friction coefficient governs
  the chassis sliding on its roof and nothing else. Setting it per surface is a number that looks
  right, reads right in a review, and changes nothing a driver can feel.
- **`CF_CUSTOM_MATERIAL_CALLBACK` with `setCombinedFriction`.** This is the correct Bullet answer for
  rigid-body wheels and for contact friction generally. It fires per contact point on the collision
  path — which the tyre never reaches. It is also a native callback into Java on the physics step,
  which G17 (headless) and G2 (fixed-step determinism) would then both have to reason about, for a
  path that does not run.

The chosen mechanism is a grid lookup on `contactPointWS` from the wheel's own raycast info, applied
per wheel in ascending index order (G3), in code this project already owns and already replays during
reconciliation (DEC-061). Slot 25 reads the same `surfaceAt` for the tyre loop, so audio and physics
cannot disagree about what a wheel is on (D16-R56).

## Rationale / Context
The concrete failure: a session implements per-surface grip through the terrain body's friction
because that is the obvious place, ships it, and every subsequent handling complaint is investigated
against a number that has never affected a tyre. The symptom is "sand feels the same as tarmac", the
cause is three layers away from where anyone would look, and the code reads as correct throughout.

This is the same shape as DISC-011 and DISC-012 — a Bullet API whose name promises one thing and
whose ray-cast-vehicle path does another — and it is being recorded before it is built rather than
after it is debugged.

## Impact
- Closes the standing gap that every arena is tarmac: the gravel tyre loop, which has shipped correct
  and unplayable since PROG-021, finally has a surface that selects it.
- Makes the surface table (D16-S4.4) the single authority for grip, rolling resistance and audio
  material, so tuning sand is one row rather than three files.
- `sand`'s rolling resistance at 4× tarmac's is the number most likely to be wrong; it is flagged in
  D16-R13 as the first thing to tune by driving.
