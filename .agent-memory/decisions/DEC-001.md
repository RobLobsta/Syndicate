# DEC-001: Own an Ashley-style component model rather than depending on Ashley or Artemis

**Date:** 2026-08-07
**Category:** decisions
**Related Docs:** docs/04_entity_component_model.md#D04-S4.1, docs/00_master_index.md#D00-S5.2
**Status:** active

## Summary
The simulation uses an in-house, component-based data-oriented model with a fixed explicit system schedule, rather than adopting Ashley (libGDX's ECS) or Artemis-odb.

## Details
Ashley's design is the right shape and we adopt it, but three requirements would each force a fork: family iteration must be ordered by ascending `EntityId` (G3), entity IDs must be network-stable with generation counters (D04-S6.1), and destruction must be deferred to a CLEANUP phase so Bullet native disposal never happens mid-step (G19, D04-S5.5). Artemis-odb performs better but its bytecode weaving complicates the headless build matrix and its ID recycling still needs wrapping.

The engine is small — entity storage, component masks, cached families, a fixed schedule, pools. Owning it costs less than bending a dependency to satisfy invariants it was not designed for.

## Rationale / Context
A future session may reasonably ask "why not just use Ashley, it ships with libGDX?" and swap it in. That swap would silently break deterministic iteration order, which is the invariant every physics regression test depends on — and the failure would look like flaky tests, not like a wrong dependency.

## Impact
`game-core`'s `ecs` package. Every system's iteration guarantees. The determinism regression suite (D12-S5.2).
