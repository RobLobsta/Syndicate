# DEC-087: a manifest that will not load leaves the part with no reference at all

**Date:** 2026-08-17
**Category:** decisions
**Related Docs:** docs/08_asset_pipeline.md#D08-S5.4, docs/07_damage_destruction_model.md#D07-S5.7, docs/03_runtime_modes.md#D03-S4.4

**Status:** active

## Summary
When a part declares a fracture manifest the loader cannot produce, `PartType.fractureManifestRef`
stays **null** rather than being set to a reference that resolves to nothing. The part then takes the
documented no-manifest path and detaches whole (D07-E5). One unreadable shard abandons the whole
manifest rather than shipping the shards that did read.

## Details
Before this session nothing ever put a manifest in the index, and the reference was set whenever
`part.json` named a file. The result was the state the game shipped in: `VehicleFactory` gave every
glass part a `FractureDataComponent` with `shardCount = 0`, and `FractureSystem` logged
`references fracture manifest … which is not loaded; destroying it without shards` every time a
windscreen died — in every match, for every pane.

Two decisions, both about which failure a player should get:

**Unset rather than dangling.** A null reference is a state D05-S4.4 and D07-E5 already describe and
the rest of the simulation already handles: the part comes off in one piece. A dangling reference is
a state only the error branch of slot 13 handles, and it makes the part *vanish* — worse than
detaching, and discovered at the moment somebody is watching rather than at load. The findings
(A107, A501, A504, A505) still name the manifest and say why, so nothing is silent; what changes is
that the consequence is the documented fallback rather than an error path.

**All or nothing per manifest.** Loading the shards that parsed and dropping the one that did not
would leave a manifest whose shards no longer sum to its part's mass. `FractureManifest`'s
constructor enforces G7 and would reject it anyway; refusing in the reader means the finding names
the missing node (A501) instead of the arithmetic.

## Rationale / Context
The concrete future failure this stops being re-litigated: a session sees `fractureManifestRef` go
null on a broken manifest, reads it as the loader dropping information, and "fixes" it by setting the
reference regardless — restoring an error log per fracture and a part that disappears instead of
falling off. This entry is the answer to why null is the deliberate value.

Both paths remain findings, so a strict start (`SYNDICATE_STRICT_ASSETS=1`, D03-S4.4) still refuses
to run on broken content. This is only about what a lenient start does (G18).

## Impact
`game-core` `asset` (`AssetLoader.loadPart`, `loadFractureManifest`). The three `game-core` test
fixture parts that declared `fracture_manifest.json` without one existing had their declarations
removed — they were a lie the loader had never been able to catch, and they now report A213 (no
manifest) rather than A107 (missing file), which is what they actually are.
