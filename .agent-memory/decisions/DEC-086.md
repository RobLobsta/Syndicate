# DEC-086: a shard is exported in its part's space and moved onto its own origin at load

**Date:** 2026-08-17
**Category:** decisions
**Related Docs:** docs/08_asset_pipeline.md#D08-S5.3, docs/09_blender_destruction_tool.md#D09-S4.4, docs/07_damage_destruction_model.md#D07-S5.6

**Status:** active

## Summary
`shards.glb` holds every shard of a part in the **part's** frame, and both readers — the collision
hull in `AssetLoader` and the drawable instance in `PartModels` — move each shard onto its own origin
by the inverse of the `localTransform` its manifest declares. The manifest's per-shard `aabbMin`/
`aabbMax` is checked against the exported geometry (A501) so that which space the file is in is
verified rather than assumed.

## Details
D08-S5.3 step 2 says `mesh = GltfLoader.loadNode(shards.glb, node = shard.name)` and then
`ShapeCache.hullFor(shard.id, mesh, 32)`, and D07-S5.6 spawns a shard body at
`partWorld × shard.localTransform`. Neither says which space the node's vertices are in, and the two
readings are not close:

| Reading | What happens |
|---|---|
| The node is already shard-local | Composing with `localTransform` places it correctly |
| The node is in part space (**what the tool writes**) | Composing applies the offset a second time; a corner pane of a 1.8 m windscreen spawns most of a metre from where it should be, and its hull's inertia is computed about a point outside itself, so it tumbles about an axis it does not contain |

The tool writes part space, and it is right to: it is what makes `shards.glb` reassemble into the
intact part when an artist opens it, and it is the frame the manifest's own AABBs and centroids are
quoted in. So the correction belongs at load, once, in `AssetLoader.toShardSpace` — vertices go to
`R⁻¹·(v − p)` and the shard keeps `localTransform` as its placement. `PartModels.shardInstanceOf`
applies the same inverse to the drawn node, because the hull you shoot and the glass you see have to
be the same object.

The AABB check is the load-bearing half. Both numbers come from the same vertices, so the only honest
difference between them is glTF's float32 round trip; a millimetre of tolerance therefore tests
*which space the geometry is in* rather than precision. Without it an exporter that ever changed its
mind would scatter every shard at twice its offset with every test still passing, which is precisely
the class of failure this project keeps finding by looking at pictures.

## Rationale / Context
The concrete future failure: someone adds a second fracture path — a progressive one, or a structure
generator — that emits shard-local geometry, and it silently loads through this reader with every
shard doubly offset. The check turns that into an A501 at load naming the shard, on the machine of
whoever made the change.

## Impact
`game-core` `asset` (`AssetLoader.toShardSpace`, `GltfShardMeshSource`, `ShardDefinition` which gains
`meshNodeName`), `game-client` `render` (`PartModels.shardInstanceOf`). No content change: the eight
shipped manifests were already written this way.
