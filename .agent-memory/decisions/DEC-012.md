# DEC-012: PhysicsWorld is injected into PhysicsSystem, and cross-tick impulses queue on it

**Date:** 2026-08-08
**Category:** decisions
**Related Docs:** docs/06_physics_simulation.md#D06-S5.4, docs/04_entity_component_model.md#D04-S4.5, docs/02_technical_architecture.md#D02-S5.7

**Status:** active

## Summary
`PhysicsWorld` is a constructor dependency of `PhysicsSystem` rather than a field on `World`, and the "pending impulses" of D06-S5.4 step 1 are a queue owned by `PhysicsWorld`, drained and applied by `PhysicsSystem` in ascending entity id order.

## Details

Two placements the blueprints leave open.

**1. Where the physics world lives.** D04-S5.4 writes `world.physics = PhysicsWorld.create(config)`, which reads as a field on `World`. `World` deliberately has no Bullet dependency (see its class comment: the physics world, asset registry and match singleton are attached by `WorldFactory`), and giving it one would make every ECS unit test load native Bullet. `PhysicsSystem` therefore takes the world in its constructor. `WorldFactory` will build both and hand the physics world to the systems that need it — slots 10, 11, 13, 14 and 15 — instead of to `World`.

**2. How forces reach Bullet.** D06-S5.4 calls `applyPendingImpulses(world)` but never says where a pending impulse is stored, and D04-S4.3's component catalogue has no force or impulse component. The alternatives were a new component (invents catalogue surface D04 does not have), a field on `PhysicsSystem` (cross-tick system state, which D04-R3 forbids), or a store on the physics world. The last one wins: it is an explicitly declared store, it is per-match, and it outlives the schedule the same way the Bullet world does.

The queue is `PhysicsWorld.queueImpulse / queueImpulseAt / queueTorqueImpulse`, each taking an entity id and copying the caller's vector. `PhysicsSystem.update` drains it before the step, sorted by `(entityId, queue order)`, and resolves the body through `RigidBodyComponent`. An impulse whose entity died between queueing and the step is dropped.

Three properties this buys:

- **Determinism (G3).** The applied order depends on entity ids and nothing else, so two runs that queue the same impulses from different systems in a different order still produce the same step.
- **No mid-tick reach into Bullet.** A system that called `body.applyCentralImpulse` directly would make the result depend on schedule position in a way the schedule does not describe (D04-R13).
- **NaN never reaches the solver.** The queue rejects a non-finite vector at the call site, where the caller is still on the stack (D00-R13).

## Rationale / Context
Without this, the first system that needs to push a vehicle — `WeaponSystem` recoil, `DamageSystem` knockback, `DetachSystem` separation — invents its own path into Bullet, and the second one invents a different path. The result is two orderings, neither documented, and a determinism failure that reproduces only when both systems fire in the same tick.

## Impact
`game-core`: `dev.syndicate.core.physics.PhysicsWorld`, `PendingImpulse`, `dev.syndicate.core.system.PhysicsSystem`. Constrains the future `WorldFactory` (D04-S5.4) and every system that applies a force.
