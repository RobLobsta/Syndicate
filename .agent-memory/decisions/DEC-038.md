# DEC-038: the damage pipeline is a shared operation, and slot 12 is only its schedule slot

**Date:** 2026-08-10
**Category:** decisions
**Related Docs:** docs/07_damage_destruction_model.md#D07-S5.2, docs/07_damage_destruction_model.md#D07-S5.9, docs/04_entity_component_model.md#D04-S4.5

**Status:** active

## Summary
The armour formulas, the damage state machine and the propagation walk live in
`dev.syndicate.core.damage.DamageApplication`, a static-shaped operation over components in the mould
of `PartDetachment` (DEC-016). `DamageSystem` (12) owns the schedule slot, the event ordering and the
burn timer, and nothing else.

## Details

**Four producers, one consumer of the arithmetic.** Damage arrives from `CollisionEventSystem` (11),
from `ProjectileSystem` (9) and `WeaponSystem` (8) through `ProjectileImpact`, from burn stacks, and
from propagation calling back into itself. A system may not call another system (D04-R13), so the
alternative to a shared operation is four copies of D07-S5.2's five steps.

**The fifth producer is a client.** D07-R26 has a client run "the same detach/fracture code as the
authority, driven by replicated events rather than by locally computed damage", and D07-S5.9's
`applyDestructionState` calls `updateDamageState` by name — the same function, reaching the same
state from the same health fraction. `DamageApplication.updateDamageState` is public and depends on
nothing but `HealthComponent` and `DamageStateComponent`, so the client half of D10 can call it
without pulling in a POST_SIM system that has no business existing on a pure client (G15).

**Instance rather than static**, unlike `PartDetachment`, because propagation is a bounded BFS with a
frontier, a visited set and a neighbour map, and allocating three collections per hit in a
fixed-timestep simulation is the kind of garbage that shows up as a frame spike rather than as a bug.
It holds nothing across a call.

**What stayed in the system.** Draining and *sorting* this tick's events, which is a scheduling
concern; ticking burn stacks, which is a per-tick pass over a family; and reading the match rules.
Those are the three things that need a slot in the schedule rather than a caller.

## Rationale / Context
A future session implementing D10's client-side reconciliation will need `updateDamageState`, and if
it lives inside a system that only exists on the authority, that session will write a second copy —
at which point two implementations of a monotonic state machine have to be kept in step, and the
symptom of them diverging is a client that thinks a part is `CRITICAL` while the server has it
`DESTROYED`. This records that the split was made for that session's benefit, not because the file
was getting long.

## Impact
`game-core` `damage` (`DamageApplication`, `HitResolution`, `CoverageMap`, `ProjectileImpact`) and
`system` (`DamageSystem`, `CollisionEventSystem`, `WeaponSystem`, `ProjectileSystem`).
