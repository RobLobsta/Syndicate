# DEC-024: the degradation table is exhaustive, and a multiplier fades toward identity

**Date:** 2026-08-09
**Category:** decisions
**Related Docs:** docs/05_vehicle_part_system.md#D05-S5.4, docs/05_vehicle_part_system.md#D05-S5.6, docs/08_asset_pipeline.md#D08-S4.2

**Status:** active

## Summary
A `(category, stat)` pair the D05-S5.4 DEGRADATION_TABLE does not name does not degrade, and a
stat's `mul` term fades toward 1 rather than toward 0: `mul' = 1 + (mul - 1) · m`. Both are
questions D05-S5.4 leaves open once its scalar pseudocode meets `StatBlock`'s add/mul pairs.

## Details
**Unlisted pairs.** The table enumerates six categories against named stats. It does not say what a
wheel's `brakeForceN` does, and D05-S4.5 says wheels contribute one. Silence is read as
`NONE` at floor 1, because the table lists `weapon / damagePerShot → NONE 1.00` explicitly — a row
it would not need if silence already meant "does not degrade". `UTILITY` is the stated exception:
"its declared stats" degrade `LINEAR` at floor 0.25, whichever stats those are.

**Multiplicative terms.** D05-S5.4's `applyDegradation` treats a stat as one scalar; a `StatBlock`
stat is an `add` term and a `mul` factor (D05-R15). Scaling `mul` by the multiplier would drive a
utility's ×0.8 fire-interval buff toward 0 as the utility died — a stronger buff from a dying part.
Fading toward identity is what D05-E3 describes ("its multipliers stop applying"): at `m = 0` the
factor is exactly 1. Inversion does not enter into it, because "worse" for a multiplier means
"closer to no effect" whichever side of 1 it started on. Only the `add` term is inverted, which is
what makes D05-E7's "1/floor = 2.5× base interval" come out exactly.

**Per-part scalars degrade from their stored value, not from the block.** `WheelController
.frictionSlip` and `WeaponController.baseFireIntervalS` are resolved at spawn against an engine
default (DEC-022/DEC-029), so their base is not recoverable from the `add` term. They degrade from
the stored scalar, which is also the form T-D05-7 and T-D05-8 state their expected values in.

## Rationale / Context
Without this, the next session extending the table cannot tell whether an absent row means "does not
degrade" or "nobody has filled it in yet", and would eventually add a row that silently changes
handling for every existing part. The multiplier rule matters more: getting it backwards produces a
vehicle whose weapons get *better* as its ammo feed dies, which reads as a balance problem rather
than as an arithmetic one and would be tuned around rather than fixed.

## Impact
`game-core` `vehicle` (`Degradation`, `DegradationRule`, `DegradationProfile`) and
`system` (`VehicleStatsSystem`). If the table should not be exhaustive, D05-S5.4 is what needs
amending — adding a "everything else" row per category the way `UTILITY` has one.
