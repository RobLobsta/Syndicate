# DEC-063: D15's slot roles are not SlotTypes, and a door is an armour panel

**Date:** 2026-08-13
**Category:** decisions
**Related Docs:** docs/15_vehicle_preparation_pipeline.md#D15-S4.1, docs/05_vehicle_part_system.md#D05-S4.3, docs/08_asset_pipeline.md#D08-S4.2

**Status:** active

## Summary
The preparation pipeline maps each D15-S4.1 label onto a real `PartCategory` and a real `SlotType`,
and D15-S4.1 was amended in the same commit to carry both columns. A `panel` — which is what a door,
a bonnet and a bumper all are — is exported as an `ARMOR` part in an `ARMOR_PANEL` slot.

## Details
D15-S4.1's "Slot role" column named `HUB`, `PANEL`, `GLASS`, `DECAL` and `INTERNAL`. None of those
is a member of `SlotType` (D05-S4.3), which has exactly seven: `ROOT`, `WHEEL`, `HARDPOINT`,
`ARMOR_PANEL`, `TURRET_MOUNT`, `ACCESSORY`, `SUBSLOT`. A `part.json` carrying one of the five does
not load, so the exporter had to either invent the mapping or emit files the loader rejects.

The mapping is constrained rather than chosen: `SlotType.acceptsCategory` has to accept each row's
category in each row's slot type, and there are only six categories. What that leaves is:

| Label | Category | Slot type |
|---|---|---|
| `chassis`, `unclassified` | `CHASSIS` | `ROOT` |
| `wheel` | `WHEEL` | `WHEEL` |
| `hub`, `drivetrain` | `UTILITY` | `HARDPOINT` |
| `panel` | `ARMOR` | `ARMOR_PANEL` |
| `glass`, `mirror`, `light`, `decal`, `grille`, `interior` | `DECORATIVE` | `ACCESSORY` |

## Rationale / Context
Two of these look like compromises and are not. **A door is an armour panel**: a part that covers a
region of the vehicle, absorbs the hits meant for what is behind it, and can be shot off is exactly
what D05 means by armour, and the fact that this one has a handle changes nothing the simulation
sees. **A hub is a utility**: it is unsprung mass bolted to the chassis with no cosmetic role at
all, and `DECORATIVE` would force its `armorValue` to zero (D08-R6) on a part that is a steel
casting.

The alternative — adding five members to `SlotType` — would put five new rows in D05-S4.3's
acceptance table, three of which accept exactly one category and would exist to serve one tool.

## Impact
- `labels.PART_CATEGORY` and `labels.SLOT_TYPE_REQUIRED` hold the table; `labels.SLOT_ROLE` is gone.
- D15-S4.1's table gains a Category column and its Slot role column now names real `SlotType`s;
  D15-R1a records why.
- `test_prepare_manifest` carries a minimal copy of `SlotType.acceptsCategory` so the two cannot
  drift without a test failing.
