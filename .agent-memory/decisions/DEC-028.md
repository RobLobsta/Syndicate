# DEC-028: a destroyed wheel is commanded to zero, not skipped

**Date:** 2026-08-09
**Category:** decisions
**Related Docs:** docs/06_physics_simulation.md#D06-S5.5, docs/05_vehicle_part_system.md#D05-S5.4

**Status:** active

## Summary
D06-S5.5's control loop reads `if w.destroyed: continue`. `VehicleControlSystem` instead writes zero
engine force, zero steering and zero grip to a destroyed wheel, because Bullet's per-wheel setters
are persistent rather than per-step.

## Details
`btRaycastVehicle::applyEngineForce`, `setBrake` and `setSteeringValue` store a value on the
`btWheelInfo` and Bullet re-applies it on every step until it is overwritten. Skipping a wheel
therefore leaves it driving and steering on the last command it received, for as long as it stays
attached — which for a destroyed part is until `DetachSystem` (14) removes it, one tick later at the
earliest and indefinitely for a part that is destroyed but not detachable.

The visible result is a vehicle that keeps pulling toward a corner that no longer works, at whatever
lock it happened to be at when the wheel died. Writing zero is what `continue` was describing.

Per-wheel friction is set the same way from `WheelController.effectiveFrictionSlip`, which slot 6
already zeroes for a destroyed wheel (DEC-024); zeroing it here as well keeps the two paths agreeing
even if one of them is later changed.

## Rationale / Context
The diff is three ternaries and looks like a stylistic preference against a `continue`. It is not:
the `continue` is a bug against this Bullet API, and a future session tidying the loop back toward
the blueprint's wording would reintroduce a vehicle that drives on a dead wheel.

## Impact
`game-core` `system` (`VehicleControlSystem`). Affects D06-S5.5's control loop pseudocode.
