# DEC-016: detachPart is a shared operation, and slot 15 triggers on its own output

**Date:** 2026-08-08
**Category:** decisions
**Related Docs:** docs/05_vehicle_part_system.md#D05-S5.5, docs/06_physics_simulation.md#D06-S5.7, docs/04_entity_component_model.md#D04-S4.5
**Status:** active

## Summary
`detachPart` lives in `dev.syndicate.core.vehicle.PartDetachment` as a static operation over components, called by both `FractureSystem` (13) and the future `DetachSystem` (14). It does **not** call `MassPropertySystem.recompute`: slot 15 detects the change itself, by comparing the mass and COM it computes against the values stored on `VehicleChassisComponent`.

## Details
Two pieces of blueprint pseudocode read as direct system-to-system calls, which D04-R13 prohibits:

- D07-S5.6 step 2 has `FractureSystem` call `detachPart(...)`, defined in D05-S5.5.
- D05-S5.5 step 3 has `detachPart` call `MassPropertySystem.recompute(vehicle)`.

**detachPart.** D07-R23 is explicit that the operation is defined once and called from two places, so it cannot live inside either system. It is a function over components in the `vehicle` package — not a system calling a system, which is what D04-R13 is about. It performs D05-S5.5 steps 1, 2 and 5: subtree removal from the slot graph in reverse topological order, `DamageState → DETACHED`, compound child removal (or wheel-index re-densification), the `structuralVersion` bump, `VehicleStats.dirty`, and one `PartDetachedEvent` per detached part. Step 4 — turning the subtree into world objects — stays with the caller, because only the caller knows whether the part fractures into shards or becomes a single debris body.

**The recompute trigger.** `MassPropertySystem` could not call back into `detachPart`'s caller, and `detachPart` calling the system directly would be the prohibited edge. The schedule already places slot 15 after slots 13 and 14 in the same tick, so a version-driven recompute satisfies G10 by construction (D04-E11). What remains is how slot 15 knows a version changed.

Remembering "the last `structuralVersion` I saw" would be cross-tick state in an ad-hoc field, which D04-R3 forbids for a concrete reason: it is invisible to replication and to rollback, and a client rewinding past a detach (D10-S5.5) would restore an older `structuralVersion` while the system still held the newer one, and skip the recompute it needs most.

So slot 15 recomputes the sum every tick — it is O(parts) and runs only on vehicles — and writes to Bullet only when the result differs from `VehicleChassisComponent.totalMassKg` / `comLocal`. Mass and COM are pure functions of the structural state, so this is equivalent to the version check; the sum is deterministic, so an unchanged structure yields bit-identical floats and the comparison is exact rather than epsilon-based.

## Rationale / Context
Both call sites look like plain function calls in the pseudocode, and implementing them literally produces either a `game-core` cycle or a system field that breaks rollback silently — the kind of bug that only appears in networked play, months later. Recording the shape once keeps `DetachSystem` (slot 14) from re-deriving it differently and ending up with two detach paths.

## Impact
`game-core` `vehicle` (`PartDetachment`, `SlotChain`), `system` (`FractureSystem`, `MassPropertySystem`), `damage` (`PartDetachedEvent`, `DetachReason`). Binds the future `DetachSystem` to call `PartDetachment.detach` rather than write its own.
