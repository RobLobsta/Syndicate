# DEC-058: the client's acknowledgement rides on its input, and a NACK is a new message

**Date:** 2026-08-13
**Category:** decisions
**Related Docs:** docs/10_networking_multiplayer.md#D10-S4.2, D10-R18, D10-S5.4

**Status:** active

## Summary
`InputCommand` gains an `acknowledgedSnapshotTick` field, and a new `SnapshotNack` message joins the
D10-S4.2 catalogue. D10-S4.2 was amended in the same commit.

## Details
D10-S5.4 defines `onSnapshotAck(peer, ackedTick)` and D10-R18 requires a client to NACK a delta whose
baseline it does not hold — and the message catalogue names no message that can carry either. Two
gaps, one answer: both are C→S, both are per-tick-ish, and the client is already sending a STATE
packet 60 times a second.

The acknowledgement is therefore a field on `InputCommand` rather than a message. A client sends
input every tick whatever else is happening, so the authority learns which baseline to delta against
within 16 ms, and a separate ACK message could only ever be later. The NACK cannot ride along that
way, because it is not periodic: it happens once, when a specific delta fails to decode, and
delaying it by up to a tick would delay the recovery it exists to trigger. So it is a message, with
its own wire id.

## Rationale / Context
The alternative for the NACK was to say nothing and wait for the authority's `SNAPSHOT_HISTORY`
timeout (3.2 s) to force a full snapshot. That works, and it means every packet-loss burst costs
three seconds of a client applying nothing — for a message that is five bytes.

## Impact
- `MessageType.SNAPSHOT_NACK` (wire id 11), `Messages.SnapshotNack`.
- `Messages.writeInputCommand` takes the acknowledged tick as its first field.
- D10-S4.2 gains a `SnapshotNack` row and R4a; `InputCommand`'s contents column gains the field.
