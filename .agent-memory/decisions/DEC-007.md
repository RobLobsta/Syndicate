# DEC-007: ECS interface is EntitySystem; LaunchConfig belongs to shared-models

**Date:** 2026-08-08
**Category:** decisions
**Related Docs:** docs/04_entity_component_model.md#D04-S4.5, docs/03_runtime_modes.md#D03-S4.2, docs/02_technical_architecture.md#D02-S4.5

**Status:** active

## Summary
Two placements the blueprints left open: the ECS system interface is `EntitySystem`, not `System`, and `LaunchConfig` plus its resolver live in `shared-models` (`dev.syndicate.model.config`) rather than in `game-core`.

## Details

**`EntitySystem` rather than `System`.** D04-S4.5 writes the interface as `System`. A type by that name in `dev.syndicate.core.ecs` shadows `java.lang.System` for every file in the package, so `System.arraycopy` and `System.nanoTime` stop resolving inside exactly the code most likely to need them. D00-E9 anticipates this collision and directs that code disambiguate; `EntitySystem` is also Ashley's name, whose shape D04-R1 adopts. Concrete systems still follow `<Noun>System` (D02-R15), so the catalogue names in D04-S4.4 are unaffected.

**`LaunchConfig` in `shared-models`.** D03-S4.2 specifies the type but not its module. Three separate executables construct one before any world exists — `game-client`, `game-server-headless`, and `test-environment` — and D02-S4.5 scopes `shared-models` to "immutable DTOs, enums, IDs ... no behaviour beyond validation", which resolution and combination-validation fit. Placing it in `game-core` would work today but would drag the simulation module into `asset-pipeline`'s dependency graph the moment the pipeline needs an asset root, violating the layering.

`RuntimeMode`, `GameMode`, `MatchPhase`, `DamageState`, `DamageType`, `PartCategory`, `CollisionLayer`, `BotDifficulty`, and `ExitCode` are placed in `shared-models` for the same reason: each is referenced across module boundaries and none carries behaviour beyond derived constants.

## Rationale / Context
A future session reading D04-S4.5 will look for an interface literally called `System`, not find one, and may add a second one — leaving two system abstractions in a codebase whose whole ordering guarantee depends on there being exactly one schedule. The `LaunchConfig` placement is the kind of thing that gets "fixed" by moving it into `game-core` unless the layering consequence is written down.

## Impact
`dev.syndicate.core.ecs`, `dev.syndicate.model`, `dev.syndicate.model.config`, and every module that boots a process.
