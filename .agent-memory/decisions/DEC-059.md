# DEC-059: a vehicle's network ids are one contiguous block, derived not sent

**Date:** 2026-08-13
**Category:** decisions
**Related Docs:** docs/04_entity_component_model.md#D04-S6.2, docs/10_networking_multiplayer.md#D10-S4.2

**Status:** active

## Summary
`SpawnEntity` carries a base network id and a block size. The vehicle takes the base, its chassis
part the next id, and every other part the ids after that in ascending slot-path order — a walk both
peers perform for themselves in `ReplicationTagging.replicatedEntities`.

## Details
Parts are entities here, and D10-S4.3 replicates per-part health and damage state, so every part
needs a wire identity. The obvious encoding — a `SpawnEntity` per entity — costs forty CONTROL
messages for a forty-part vehicle at every spawn, and every respawn in a match.

The block works because the ordering is derived from content rather than from runtime state. Slot
paths come from the assembly file (D05-R11) and are identical on every peer; entity ids are not,
because they depend on what else that world has spawned and recycled. So the walk is sorted by slot
path, with the chassis part pinned first as the one part that cannot detach (D05-R26).

The cost is that the two peers must build the same assembly the same way. They do — both go through
`VehicleFactory` — and the handshake's content hash is what catches the case where they would not
(D10-R11).

## Rationale / Context
If a future change makes part creation order depend on anything but the assembly file, this breaks
silently: the client binds the authority's health to the wrong part and a car appears to take damage
where it was not hit. The defence is that `replicatedEntities` is one short method, is used by both
peers, and sorts explicitly rather than trusting insertion order.

## Impact
- `ReplicationTagging`, `NetworkRegistry.allocateBlock`.
- `Messages.SpawnEntity` carries `baseNetworkId` and `blockSize`.
