# DEC-088: one tool per transform, and the destruction class is a required argument

**Date:** 2026-08-17
**Category:** decisions
**Related Docs:** docs/09_blender_destruction_tool.md#D09-S5.3, docs/15_vehicle_preparation_pipeline.md#D15-S5.7, docs/00_master_index.md#D00-S6

**Status:** active

## Summary
`syndicate_fracture` authors the FRACTURE transform and nothing else; the deformation stage is a
second package, `syndicate_deform`. Both take `--destruction-class` as a **required** argument,
consult the shared `syndicate_policy` table, and exit 77 rather than authoring a transform D15-S5.7
does not give that class. Each also rejects the other's flags with exit 64 naming the other tool.

## Details
The tool ran both stages unconditionally on every mesh — `--shards 24` and `--damage-morphs 4` were
both defaults — so the documented D09 invocation produced a part that dented *and* shattered, which
no class in D15-S5.7 receives (DISC-068). It was not even symmetric: `--damage-morphs 0` disabled
deformation, and `--shards` was clamped to `[2, 256]`, so the tool could not be asked *not* to
fracture.

Three decisions inside this one, each with an alternative that looks reasonable:

| Decision | The alternative, and why not |
|---|---|
| Two packages, not one tool with a mandatory `--transform` | A mode flag leaves both code paths in one pipeline and one `Args`, which is exactly the arrangement that let them run together for eleven sessions. Two packages cannot be asked to do each other's job. |
| The class is **required**, with no default | A default restores the silence: a tool that assumes `GLASS` fractures whatever it is handed, and one that assumes nothing cannot refuse. Requiring it costs each caller one argument. |
| Exit **77**, not 64 | The invocation is well formed; the *content decision* behind it is what is wrong. An agent's response differs — fix the part's label or call the other tool, not the flags — and D09-R5 exists so an agent can branch on that without parsing a report. |

The old flags are still parsed rather than removed. Dropping them would leave every existing
invocation looking like it still worked while quietly authoring one transform instead of two, which
is the same failure in the other direction; they now exit 64 with a sentence naming the other tool.

The transform names are **D00-S6's**, not new ones. The glossary already defines *fracture* as "the
one-time replacement of a part's single rigid body with its pre-authored shards" and *deformation*
as "continuous visual mesh change driven by shape keys", each with the note "not the other". An
earlier draft of `blender-tool/README.md` proposed renaming the package to `syndicate_shatter`; that
was wrong, and inventing a synonym for a glossary term is the loose usage CLAUDE.md warns outlives
the session. The package was always named correctly — it simply did a second thing its name did not
cover.

## Rationale / Context
The concrete future failure: D15-S5.7 is amended to give shards to a second class, somebody runs the
fracture tool over a batch of panels to produce them, and every panel comes back with dent morphs it
must not have. Under the old arrangement nothing would have said so — not the tool, not the fixture
gate, not the loader, not the engine.

## Impact
`blender-tool/`: new `syndicate_policy` (the class/transform and exit-code tables, no `bpy`) and
`syndicate_deform` (CLI, pipeline, manifest, self-verification, `morphs.py` moved in);
`syndicate_fracture` loses its morph stage; `syndicate_prepare.destruction` delegates the table and
`exporter.fracture_glass` becomes `author_fracture`. D09-S4.2, S4.3, S5.1 and S5.3 amended in the
same commit. `TV-002`/`TV-003` follow the shape keys they check into the deform tool; ids are
permanent and are not reused (D09-S7).
